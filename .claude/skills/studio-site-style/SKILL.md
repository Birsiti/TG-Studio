# Сайты студии — техника и идентичность

Фундамент для многостраничных сайтов Студии ботов (сам tg-studio.by и
будущие клиентские маркетинговые сайты) — в паре с `miniapp-style`, который
покрывает одностраничные Mini App продукты. Не путать области: если файл
открывается как Telegram Mini App из бота — это `miniapp-style`; если это
сайт с несколькими URL, который индексирует поисковик, — этот скилл.

## Когда голого HTML уже недостаточно

Один `index.html` без сборки — нормальное состояние для landing page с одной
задачей (как раньше был tg-studio.by). Но как только у сайта появляется
вторая осмысленная страница — раздел услуг с отдельными URL, кейсы, блог —
голый HTML начинает или дублировать вёрстку в каждом файле, или скатываться
в SPA с якорной навигацией (`#services`, `#faq`), которую поисковик не
индексирует как отдельные страницы. Оба варианта — тупик.

**Решение — Astro** (`npm create astro`, output: static). Причины именно
Astro, а не Next/Vite+React/что-то ещё:
- Файловая маршрутизация — `/mini-apps`, `/keysy/[slug]`, `/novosti/[slug]`
  без ручного роутера.
- Content collections — новости и кейсы как markdown-файлы с frontmatter,
  без хардкода контента в компонентах (см. ниже).
- Встроенная оптимизация картинок (`astro:assets`, компонент `<Picture>`) —
  AVIF/WebP с fallback и явными width/height без отдельного пайплайна.
- Выход — чистый статический HTML, JS почти не нужен, что и держит
  Lighthouse Performance высоким без борьбы с гидратацией фреймворка.

Мигрируя существующий одностраничник, переноси разметку 1:1 (текст, классы,
JS-поведение форм и т.п. не трогать без явной просьбы) — задача техническая,
не редизайн. CSS из одного огромного `<style>` можно разбить по секциям
(`base.css`, `header.css`, `hero.css`, …), импортируемым в один `global.css`
— так проще искать нужный кусок, а собранный CSS на выходе не меняется ни
на байт.

## netlify.toml, если сайт лежит в подпапке репозитория

У студии частый паттерн — один репозиторий на несколько проектов, сайт
лежит не в корне. Netlify UI сам не знает про Astro-сборку, если раньше
отдавал папку как статику "как есть" — добавь `netlify.toml` в корень репо
явно:

```toml
[build]
  base = "Название Папки С Сайтом"
  command = "npm run build"
  publish = "dist"
```

После первого мержа с таким файлом проверь в Netlify UI (Site settings →
Build & deploy), что там нет старых ручных настроек base/publish, которые
могут переопределить `netlify.toml`.

## SEO-каркас — обязательный минимум на каждом сайте студии

Не бонус, а часть определения "сайт готов":

- **Уникальные `<title>`/`<meta description>`/`<link rel="canonical">` и
  ровно один `<h1>`** на каждой странице, не только на главной.
- **Хлебные крошки** (`BreadcrumbList` JSON-LD + видимая разметка) на всех
  страницах кроме главной — текст в разметке должен дословно совпадать с
  видимым текстом крошек, иначе Google это как минимум проигнорирует.
- **JSON-LD**: `Organization` на каждой странице, `LocalBusiness` на
  главной, `FAQPage` вокруг реального FAQ-блока (не выдуманного для
  разметки), `Service` на страницах услуг. Генерировать из тех же
  JS-переменных/массивов, что рендерят видимый текст — никогда не писать
  разметку отдельно от контента, иначе они разъедутся при следующей правке
  текста.
- **sitemap.xml — генерируется при сборке**, не лежит как статичный файл.
  Простой Node-скрипт (`scripts/generate-sitemap.mjs`, запускается после
  `astro build` через `&&` в `package.json`), который берёт список
  статических роутов + перечисляет файлы в content collections — тогда
  новая статья в sitemap попадает сама, без правок скрипта.
- **hreflang-заготовка**, даже если сейчас только один регион/язык: одна
  запись на текущую локаль + `x-default`, обе указывают на тот же URL.
  Когда появится второй регион (RU/KZ и т.п.) — добавляется запись, а не
  переписывается вся схема.
- Гео-факты (город, страна, зона обслуживания) — в один конфиг-модуль
  (`src/site.config.js`), не хардкодить строками по разметке. Ровно тот же
  принцип, что и с цветами ниже: один источник правды.

## Новости/блог — файловый контент, без хардкода

Content collection (`src/content/news/*.md`, frontmatter: title,
description, category, date, plus поле для связки со страницей услуги,
например `relatedService`). Slug страницы = имя файла — значит, новая
статья это buквально один `.md`-файл, без единой правки кода. Список с
фильтром по категории на клиенте (просто скрывать карточки по `data-`
атрибуту — HTML всё равно статически содержит все статьи, так что для
краулера фильтр прозрачен). На карточке статьи — блок похожих статей той
же категории и ссылка на связанную коммерческую страницу (через
`relatedService`) — это тот самый внутренний линкинг, который двигает SEO
у сервисных страниц.

Тот же паттерн подходит для кейсов (`src/content/keysy/*.md`) — один файл
на кейс, готово под будущие кейсы без переделки шаблона.

## Идентичность: не выдумывай новую палитру — возьми токены продукта

Если сайт принадлежит самой студии (не внешнему клиенту), у него уже есть
готовая, узнаваемая, невозможная-к-копированию айдентика — реальный дизайн
Mini App продуктов, описанный в `miniapp-style`. Сайт-визитка со стандартным набором
тёмный-фон-плюс-один-акцент — это ровно то, чем выглядит любое
dev/AI-агентство в 2026. Вместо этого:

- Взять базовые токены `miniapp-style` (`--bg`/`--surface`/`--ink`,
  `--accent`, `--ok`, радиусы `14px`/`10px`) и адаптировать под масштаб
  маркетингового сайта, а не изобретать новую палитру с нуля.
- Использовать `--ok` (тил-зелёный из чекмарков "Запись подтверждена" на
  реальных скриншотах продукта) как второй акцент с собственной ролью —
  proof/результат/успех — а не декоративное дополнение к основному
  `--accent`.
- Шрифтовая тройка студии (дисплейный геометричный + гуманистический sans +
  JetBrains Mono для данных/цифр/лейблов) — тоже часть айдентики, не
  дефолт по вкусу; смотри `miniapp-style` за именами конкретных шрифтов.
- Если на сайте есть реальные скриншоты продукта (кейсы) — это и есть
  главный визуальный актив, product-first hero сильнее любой абстрактной
  иллюстрации или 3D-рендера телефона.

Для внешних клиентов (не самой студии) эта секция не применяется буквально
— но тот же принцип: искать, что уникально узнаваемо именно у этого
бизнеса, вместо генерик-темы под нишу.

## Превью на GitHub Pages без траты билд-минут Netlify

Полезный трюк, если Netlify на лимитированном тарифе, а нужно быстро
показать промежуточный результат: собери сайт локально (`npm run build`),
перепиши все root-relative пути под сабпуть GitHub Pages
(`/<имя-репозитория>/`) — Astro сам этого не делает, если `base` не
выставлен в конфиге, а трогать `base` ради временного превью не стоит
(сломает продовую сборку под кастомный домен). Простой Node-скрипт
регэкспом заменяет `href="/`, `src="/`, `srcset="/` на префикс с сабпутью
только в скопированной `dist/`, затем результат коммитится в ветку
`gh-pages` (классический branch-deploy, без GitHub Actions — так надёжнее
и не упирается в защиту `environment: github-pages`, которая по умолчанию
разрешает деплой только с default-ветки). Не забыть `.nojekyll` в корне
ветки — иначе Jekyll молча выкидывает папки с подчёркиванием вроде
`_astro/`, которые генерирует Astro.

Если у пользователя уже включён GitHub Pages, но сайт не открывается — в
первую очередь проверь, из какой ветки/папки он реально собирается
(Settings → Pages → Source): частый случай — Pages настроен на `main`,
где лежит вообще другой проект без `index.html` в корне, а не на что-то
специально подготовленное.
