# cake-warehouse — «Милано» (бывший ТОРТОВОЗ)

Склад тортов с развозом по городам и оптовый заказ. Заказчик — кондитерская «Милано» (ООО, milano.by);
с 22.10.2026 бот — @Milano_BY_Bot (прежний @Tort_BY_bot больше не используется), оформление в стиле
milano.by (`brand.css`, логотип `img/milano-logo.svg`). Пути файлов не трогать — на них ведут кнопки Web App
бота (`cake-bot/src/roles.js`). «Сделать заказ» на главной ведёт в оптовую витрину tort.tg-studio.xyz (iMac `~/tort-opt`). LEADTEX не используется.

**Где мы сейчас — [`docs/status.md`](docs/status.md)**: что запущено на iMac,
решения клиента, открытые вопросы. Скилл проекта — `.claude/skills/cake-warehouse/`.

## База под реальный процесс

`db/` — SQLite-схема по заявкам клиента: маршрут → заказчик → точка →
заявка → сводная маршрута (лист сборки: сборщик, ящики, стопки) →
отгрузка → возвраты и тара по точкам. 11 заявок с фото сверены с «Итого»
(`db/check_db.py`). Схема — `db/schema/01…08_*.sql`. Заявки с фото — общие с API
(`api/bots/cake/orders_data.py`). В API уже есть сборка (`picking.py`: точки,
заявки, галочки, места, `routeToTrip`): собранный маршрут → черновик рейса,
маршрут хранится как строка `cities` (направление рейса), остальная цепочка
рейса не менялась.

## Учёт

- Остаток = сумма журнала `moves` (qty со знаком). Ничего не редактируется
  задним числом: ошибку исправляют пересчётом (`adjustStock` пишет разницу).
- Рейс: `draft` (сборка, остаток не трогает) → `shipTrip` списывает
  торты и записывает ящики на водителя → `shipped` → водитель `reportTrip`
  → `reported` → кладовщик `closeTrip`: годные возвраты обратно на
  остаток, брак только фиксируется в рейсе, ящики снимаются с долга водителя.
- Ящики (оборотная тара) числятся **за водителем**: `tara_moves.kind` out
  (выдали при отгрузке) / back (вернул при приёмке или позже) / writeoff
  (утерял — долг списан). Долг водителя = сумма; на складе = всего − долги
  − утеряно. Стопки — не тара, это количество для погрузки в листе сборки.
- Нет ежедневного «освежения» демо и нет обрезки старых строк — это учёт.

## Доступ

`TGS_CAKE_ADMINS=<tg id>,<tg id>` в окружении API включает рабочий режим:
пускаются только эти id и активные сотрудники с заполненным Telegram id
(справочник «Люди»). Роли проверяет сервер (`_guard` в `base.py`): водителю —
только `DRIVER_ACTIONS` (свои рейсы, справочник, отчёт по своему рейсу),
`saveStaff` — только руководителю из `TGS_CAKE_ADMINS`, кладовщику — всё
остальное. Без обеих переменных — открытое демо; токен без списка
руководителей — пускаются только сотрудники.

`TGS_CAKE_BOT_TOKEN=<токен из @BotFather>` включает проверку подписи
Telegram (`verify_init_data` в `api/core.py`, срок 24 ч): запрос без
подписи этого бота отклоняется (`forbidden`), а пользователь берётся из
подписи, не из `userId`. Токен — только в окружении API на iMac, в
репозиторий не коммитить. Боевой режим = обе переменные.

## Данные

- **Ассортимент — реальный**: 94 позиции из заявок клиента (фото накладных
  от 17.10.2026, `source/`), `CATALOG` в `api/bots/cake/catalog.py`, 5 категорий: Торт, Венский
  десерт, Пирожное, Набор пирожных, Сладости мучные. Одно название бывает
  в разных весах (Сникерс 0,4 / 0,8 кг) — везде показываем «название, вес».
  `mock-data.js` содержит тот же список: правка только в `catalog.py`, потом
  `python3 db/gen_mock_catalog.py`.
- Тара — только «Ящик»; сколько всего в обороте — посчитать на складе
  (сейчас заглушка 500).
- На iMac база **рабочая** (`~/tg-studio-data/cake.db`): не удалять и не
  пересоздавать. Схема меняется только миграцией (`orders_seed.migrate_picking`,
  идемпотентно, при каждом старте), перед обновлением — копия в `~/backup/`.
